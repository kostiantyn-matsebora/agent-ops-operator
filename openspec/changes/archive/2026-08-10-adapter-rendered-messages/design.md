## Context

Today an outbound op is a string:

```go
type Op struct {
    ID, Channel, Conversation string
    Kind     OpKind   // ensure-topic | send
    Title    string   // ensure-topic
    ThreadID *string
    Text     string   // send payload (chat HTML subset)
}
```

Every caller pre-renders. `router.go` writes `<b>` tags and `&lt;` escapes;
`relayToSiblings` composes `💬 <b>origin/sender</b>: text`; `/work/done` passes
the agent's output through untouched. The adapter is a pipe.

Facts that shape the design:

| Fact | Consequence |
|---|---|
| `channel-telegram/telegram.go:75` sends `text` verbatim to `sendMessage`; Telegram caps at 4096 | Nothing handles length today; a raw alert payload fails the op rather than truncating |
| Ops declare "chat HTML subset" | A payload containing `<`, `>`, `&` breaks parsing unless escaped by whoever renders |
| Signal payloads are stored out-of-line as `ConversationInput` precisely to keep etcd objects small | Inlining them into ops is a memory question, not an etcd one |
| `OpQueue` is in-memory and lossy by design; ensure-topic is regenerated by reconciliation, sends are fire-and-forget | Input cards need a stable id to survive reconcile-driven re-enqueue without duplicating |
| `FanOutSend` skips channels with no thread binding | A card enqueued before `ensure-topic` completes would silently vanish |
| In-process `Registry` providers consume the same ops as external adapters | They are a second renderer implementation, not an exemption |
| The `?type=` → `?adapter=` retirement returns 400 naming the replacement | Precedent for failing an outdated adapter loudly instead of serving it nothing |

Requester decisions carried in: one change, not two; topics are structured too
and named by the adapter from its own template.

## Goals / Non-Goals

**Goals:**
- The manager composes *meaning*; adapters compose *presentation*. No transport
  dialect anywhere in `internal/`.
- A conversation thread reads as: the event, then the work, then the answer.
- Length, escaping, and truncation are decided by the component that knows the
  limits.
- Multi-channel fan-out can look different per surface from one semantic
  message.

**Non-Goals:**
- Changing what the agent writes — `format.md` still governs that.
- Progress/lifecycle streaming into chat (the project deliberately avoids
  stream-of-consciousness walls).
- A payload-fetch endpoint on the contract.
- Backward compatibility with string-valued ops.

## Decisions

### D1. Four message kinds, typed fields, markdown prose

```
signal   {pipeline, source, title, labels{}, body, inputRef}
answer   {body, status}
relay    {origin, sender, body}
notice   {level, body}
```

`pipeline` is filled from inference (D1b) and may be empty; `source` comes from
the input's stored origin.

The split between typed and free-text is the whole design. `labels` stays a map
so Telegram can render `k=v` inline while a web chat renders a table and a
future adapter renders nothing at all. `body` is markdown because the
alternative — fully structuring prose — would mean parsing the agent's output
into fields, which `format.md` deliberately leaves as human-authored text.

Markdown as the interchange means adapters convert *one* known input format
rather than un-parsing Telegram HTML. An adapter that cannot be bothered may
concatenate the fields and send them plain; the contract does not demand
fidelity, only that presentation is the adapter's call.

Rejected: keeping `text` alongside the structured fields as a fallback. It
would leave the manager rendering, which is the thing being removed, and the
fallback would rot into the real path.

### D1b. The SOURCE is stored per input; the PIPELINE is inferred

A card naming its pipeline and source needs both at render time, and they are
not symmetric.

**The source is stored.** It is captured today only as a side effect —
`signals.go` writes `InputItem.JobName = source.Name` for `kind: job` and drops
it for every other kind — and it is genuinely underivable afterwards: nothing on
the Conversation records which source fired which input. So `InputItem.Origin`
(`{kind: signal|channel, name}`) replaces `JobName`. Per-input rather than
per-conversation, because a conversation accumulates inputs over time and a
recurrence should be able to say which source fired it even if a later input
arrived another way.

**The pipeline is inferred.** `Conversation` carries no `pipelineRef`, and this
change does not add one:

- `mcp-toolset-model` states it as a requirement — "materialized
  per-conversation state, following the profileRef/channelRefs pattern; no
  `pipelineRef` is introduced" — and `CLAUDE.md` repeats it as binding
  terminology. `pipeline-addressed-conversations` landed without adding it.
- `chat.PipelineForConversation` (`internal/chat/pipelines.go:78`) already
  derives the pipeline from the materialized bindings, and `server.go` uses it
  to attribute every dispatch and completion event. It returns blank when the
  wiring is ambiguous, deliberately: `docs/console.md` documents attribution as
  INFERRED and "left blank when ambiguous — never guessed".

So the renderer takes the pipeline from that helper and omits it when it comes
back empty. A card that cannot name its route says less; it never says something
false. This is the same posture `/status` and the console already take, so a
blank pipeline on a card is consistent with the rest of the product rather than
a new kind of gap.

The original argument for storing it — "reconstructing at render time is not
available, because the card is enqueued in the reconciler far from the
`routeSignalGroup` call that held the objects" — mistook *proximity* for
*availability*. The helper needs only the Conversation and a client, both of
which the reconciler has.

Two things still fall out of `Origin`. The posting rule (D5) becomes a property
of the input rather than a type lookup extended every time an input type is
added. And "which source fired this input?" becomes answerable from the CR
alone, which it is not today.

Cost: one optional CRD field where the earlier draft added two. Existing inputs
carry no origin; D5 states what that means rather than leaving it to a nil
check.

### D2. `ensure-topic` carries a descriptor; the adapter names the topic

`{conversation, pipeline, source, title, labels{}, kind}` instead of a baked
`Title` string.
Telegram forum topic names cap at 128 characters and cannot be markdown; a web
chat has no such limit and may want the labels in the name. Same reasoning as
D1, applied to the one op that was already half-structured.

Consequence worth stating: the topic name and the first card in the thread are
rendered from the *same* descriptor data by the same adapter, so it can choose
not to repeat itself — put the alert name in the topic and the labels in the
card, rather than both in both.

### D3. Payloads are inlined in the op, not referenced

The adapter has no Kubernetes access and no way to read a `ConversationInput`.
The options were a fetch endpoint on the contract or inlining. Inlining wins:
one round trip, no new endpoint, no auth surface, and it is what makes
attachment rendering possible — Telegram can `sendDocument` the full JSON only
if it *has* the full JSON.

`inputRef` still travels (the `ConversationInput` name) so an adapter can cite
where the full event lives for anyone with cluster access. It is named
`inputRef` rather than `sourceRef` deliberately — with D1b, `source` on the same
message means the `SignalSource`, and two fields a letter apart meaning
different objects is the kind of naming that produces a bug per adapter.

Cost: a large payload sits in the in-memory `OpQueue` until claimed. Bounded by
conversation volume and op lifetime (`ReclaimAfter` is 5 minutes), and the
manager already holds the payload transiently when routing the signal. Recorded
as a risk rather than pre-optimized.

### D4. Input cards are enqueued on thread binding, with a stable id

The card cannot be enqueued at conversation creation — `FanOutSend` skips
channels with no thread yet, so it would be silently dropped. It is enqueued
when the binding lands, which is also what makes it *parallel to dispatch*
rather than sequenced with it: the agent starts working while the card posts.

Id is `input:<conversation>:<inputID>:<channel>` — stable, so the reconciler's
re-enqueue dedups against both the pending map and the `recent` window, exactly
as `topic:<conv>:<channel>` already does. Without this, every reconcile of a
conversation would repost its alert.

### D5. "Post what a human has not already seen" is the posting rule

Not "post signals" — the general rule is shorter and answers more:

| `origin.kind` | reaches the manager as | posted | why |
|---|---|---|---|
| `signal` | `alert`, `job`, `task` signals → `alert`/`job`/`task`/`recurrence` inputs | yes | the event nobody in chat has seen |
| `signal`, but `kind: chat` | a chat signal from a chat source | **no** | the surface the person typed on already showed it; siblings get it via `relayToSiblings` |
| `channel` | a `/<pipeline>` command, a thread reply | no | same reason, one path earlier |
| absent (pre-upgrade inputs) | — | no | an input that predates provenance describes an event already delivered or long past; posting it on the next reconcile would spam every open thread at upgrade |

With D1b the rule reads mostly off `origin.kind` rather than enumerating input
types, so a new input type inherits correct behavior instead of silently
defaulting to "posted" or "not posted" depending on which branch someone forgot.

**Chat is the one exception, and it is a `signal` origin.** Since
`chat-signal-origination` landed, a general-surface message arrives through a
`SignalSource` exactly like an alert, so origin kind alone would post a card
echoing what the user just typed back at them. The signal's own `kind: chat` is
what excludes it. That is one enumerated case, stated here and carried onto the
input, rather than the type-lookup this rule exists to avoid.

The rule is evaluated per input, not per conversation, so a recurrence on a
week-old conversation posts into the existing thread — which is exactly the
behavior that makes a thread an incident log.

`POST /task` had its own origin kind (`api`) in an earlier draft. `task-is-a-signal`
removed that endpoint, so a programmatic task is a `kind: task` signal through a
claimed source: `signal` origin, posted, no special case. The enum is two-valued.

### D6. Adapters declare the contract version; old ones fail loudly

An adapter built against string ops would receive messages with no `text` field
and post empty strings — a silent, confusing failure. So `/channel/ops` requires
the adapter to declare the contract version it speaks, and rejects an absent or
outdated declaration with 400 naming the replacement. This is the posture the
`?type=` retirement already established, and the reason to prefer a hard break
over a compatibility shim.

### D7. In-process providers are held to the same contract

`internal/chat/provider.go`'s registry providers consume the same ops, so they
get renderers too. Exempting them would put presentation logic back inside
`internal/` through the side door — the exact leak this change closes.

## Risks / Trade-offs

- [Every adapter must be updated in lockstep with the manager] → Breaking by
  design, with D6 making the failure loud. There is one reference adapter and
  the in-process registry in-tree; third-party adapters are the accepted cost of
  fixing this at `v1alpha1` rather than after.
- [Presentation quality now varies per adapter, and a lazy adapter renders
  badly] → True, and correct: a bad renderer is visibly one adapter's bug rather
  than a central compromise. The reference adapter sets the bar.
- [Large payloads inflate the in-memory op queue] → D3's trade-off. Mitigated by
  short op lifetime; if it bites, a size cap plus a fetch endpoint is an additive
  follow-up, not a redesign.
- [Threads get noisier — two messages per conversation instead of one] → One
  extra message per *input*, not per signal; cooldown and signature grouping
  already bound how many inputs a conversation receives. Chat and replies are
  excluded by D5.
- [Alert labels can carry sensitive detail into a shared chat] → Real, and this
  change makes it visible where it was previously buried in a CR. Whether the
  card is suppressible per source or per pipeline is an open question, not
  silently decided.
- [Markdown is underspecified — adapters may disagree on what subset is safe] →
  The contract should name a conservative subset rather than "markdown". Listed
  as a task; getting this wrong reintroduces the leak in a new dialect.
- [Duplicate cards if the stable id is wrong] → D4's id is pinned by a test that
  reconciles a conversation repeatedly and asserts one card.
- [Inference leaves the pipeline blank on cards where two Ready pipelines could
  claim the conversation] → Accepted, and the whole reason D1b chose inference:
  a blank is the honest answer the product already gives in `/status` and the
  console. If it turns out to matter often, storing the ref is an additive
  follow-up that would then have evidence behind it rather than an assumption.
- [Existing inputs predate `Origin`, so their cards have no provenance] → The
  field is optional and an absent origin means NOT POSTED (D5), so upgrading
  cannot spray cards for old inputs into every open thread on the first
  reconcile. New inputs get cards; in-flight threads are unchanged.

## Migration Plan

Manager and in-tree adapters move together; there is no partial state worth
supporting.

1. Define the message and topic-descriptor types and the version handshake;
   manager still sends the old shape. Nothing changes behaviorally.
2. Teach `channel-telegram` and the in-process providers to render the new
   shape, gated on the declared version.
3. Flip the manager to structured ops and delete the HTML strings from
   `internal/`.
4. Add the input card (D4, D5) — the first thing the new contract enables that
   the old one could not express.
5. Docs, and the `CLAUDE.md` invariant.

Rollback: steps 3 and 4 revert together; steps 1–2 are inert on their own.
Adapters that already speak the new version keep working against a reverted
manager only if the version handshake tolerates both, which it deliberately does
not — so rollback means reverting adapters too.

## Open Questions

- **Which markdown subset?** "Markdown" is not a spec. Bold, italic, inline
  code, fenced code, and links cover every current message; anything more should
  be justified per use. Needs naming in the contract before adapters diverge.
- **Is the input card suppressible?** Per-source or per-pipeline opt-out for
  installs where alert bodies should not reach a shared surface. Default on.
- **Does `notice` need levels beyond info/warn?** Errors currently surface as
  Conversation conditions, not messages; if that stays true, `level` may be
  two-valued forever.
- Whether `answer` should carry the agent's chosen `format.md` template as a
  hint, so adapters can style an investigation differently from an action
  report. Attractive, and entirely speculative until an adapter wants it.
