## Context

agent-ops already keeps most of its state in the Kubernetes API: configuration is CRs, conversation state (`sessionId`, `threads`, `inputs`, `runs`, `phase`) is `Conversation` status, adapter cursors are annotations on `Channel`/`SignalSource`, and admission is counted from the live pod list rather than from status. Those parts already survive a restart by reading.

Three gaps remain, and each was found by tracing a restart rather than by reading a TODO:

1. **`/data/home` is ephemeral by default.** `chart/values.yaml` provisions the home PVC only under `persistence.enabled`, which ships `false`. `Conversation.status.sessionID` is durable but the session *files* under `$HOME/.claude/projects/-data-workspace/` are not, so after a runtime pod restart `runtime-claude/runtime.js` hits its "resume produced no output" path, retries as a new session, and prefixes the answer with a warning. State exists in two places and only one of them is durable.
2. **The reply `send` op is not derivable.** `internal/httpapi/server.go` records the run result into `Conversation.status`, then calls `Router.FanOutSend`, which enqueues into the in-memory `OpQueue`. A manager restart in that window loses the op, and nothing regenerates it — the answer sits in `status.runs[].result` forever, undelivered. `ensure-topic` is regenerated by reconciliation; `send` never was. The `OpQueue` doc comment claims send ops are "fire-and-forget UX (send acks)", which was true when the only sends were acks and is no longer true now that replies travel the same path.
3. **The ingest cooldown is process memory.** `internal/ingest.Cooldown` holds `seen` in a map, with a comment accepting "restart resets the window, which only risks one duplicate investigation". With `MAX_QUEUED_CONVERSATIONS` and a flapping alert source, a restart during an incident costs more than one duplicate.

`/data/workspace` is always `emptyDir`. That is not a bug — a fresh clone is correct — but it means a runtime pod restart mid-conversation discards uncommitted agent work.

Constraints inherited from the codebase: the manager reads no Secrets; the operator grants adapters no RBAC; every op must be derivable from CR state (with `close-topic` the documented exception); `/data/workspace` cannot move, because claude-code keys sessions by cwd.

## Goals / Non-Goals

**Goals:**

- A restart of any component recovers current state, with the losses that remain named and bounded.
- One stated rule for where state lives, so future state has an obvious home.
- Session persistence works out of the box rather than after reading a values comment.
- Optional workspace persistence for installs that want uncommitted agent work to survive a pod restart.

**Non-Goals:**

- Manager high availability or multiple active replicas. Leader election stays as it is; this change makes a *restart* lossless, not a second replica possible.
- Moving activity telemetry to external storage. It stays bounded, in-memory and lossy — the change is that it reports its gaps.
- Any storage in the console, or any console write path to the Kubernetes API.
- Exactly-once delivery. Ops stay at-least-once; adapters still de-duplicate by op id.

## Decisions

### D1: Two homes for state, chosen by what the state is — and the manager mounts nothing

Filesystem state goes on a PersistentVolume. Everything else goes in the Kubernetes API.

*Why:* the API is already durable, already the manager's source of truth, and already survives the manager landing on a different node. A PVC for manager state would pin the manager to one node (RWO) or add a distributed-filesystem dependency (RWX) to gain nothing the API does not already give, and it would create a second source of truth beside the CRs — which is precisely the failure mode gap 1 exhibits.

*Alternatives considered:* a manager state volume for the op queue and cooldown (rejected: node affinity, second source of truth); an external store such as Redis (rejected: a new runtime dependency for a project that deliberately has none, and every fact involved already has a natural CR to live on).

### D2: Delivery becomes a fact on the Conversation, not an entry in a queue

Add a per-run, per-thread delivery marker to `Conversation.status.runs[]` (channel names already delivered). Introduce a **stable op id** for run replies — `send:<conversation>:<channel>:<runId>` — replacing the `sendSeq` counter for this class of send. Ack and notice sends keep their counter-based ids and stay fire-and-forget, which is what they are.

Two paths produce the reply, and they cannot collide:

- **Fast path**: `/work/done` records the result, then enqueues the reply as it does today. Latency is unchanged.
- **Backstop**: the conversation reconciler enqueues a reply for any completed run whose result is recorded and whose bound thread lacks a marker.

The stable id makes the two idempotent against each other — the queue's existing dedup on op id already covers "queued or recently completed". Marking happens when the op completes, so an op lost before completion is re-derived, and one completed before the restart is not.

*Why per-thread rather than per-run:* fan-out to three channels can be interrupted after one succeeds. A per-run boolean would either re-post to the delivered thread or abandon the other two.

*Alternatives considered:* persisting the whole `OpQueue` to a ConfigMap (rejected: makes the queue a second source of truth, and the queue's contents are already derivable — the missing piece was the derivation, not the storage); a `Delivered` condition per channel (rejected: conditions are for reconciliation outcomes, and this is per-run history, so `runs[]` is where it belongs).

### D3: Cooldown is recorded on the SignalSource, written only when a fingerprint is fresh

`SignalSource.status` gains a bounded list of `{fingerprint, at}`. The in-memory map stays the hot path; it is loaded from the CR on first use per source after a restart. Entries are pruned past their window.

The write rate is the key point: only a **fresh** fingerprint writes, and a fresh fingerprint already causes a `Conversation` create or patch. Suppressed signals — the high-volume case that cooldown exists for — write nothing.

*Alternatives considered:* deriving cooldown from live `Conversation` objects, since a fresh fingerprint always produces or extends one (rejected: `/close` deletes the Conversation, which would silently end suppression and let a still-firing alert re-open immediately — today's behavior correctly keeps suppressing); a ConfigMap per source (rejected: a second object to reconcile and GC for state that belongs to the source).

### D4: Home persistence ships on; workspace persistence ships off

Home on, because losing it silently costs conversational history and the loss is invisible until an agent answers without context. Workspace off, because a fresh clone is always correct and a stale shared checkout is not — persisting it is an optimisation and a convenience, not a correctness fix.

`AgentRuntime.spec` gains `workspace` alongside `home`, shaped identically (`pvcRef` / `emptyDir`). The chart provisions a second claim under `persistence.workspace` and wires `workspace.pvcRef` the same way `home.pvcRef` is wired today — from the parent's own values, never restated by the operator.

### D5: Workspace isolation is `subPath` per conversation, and the mount path does not move

Each runtime pod mounts `<claim>/<conversation-name>` at `/data/workspace`. The container sees the same path it sees today, so cwd-keyed session resume is unaffected; the claim holds one directory per conversation, so concurrent pods cannot observe each other's tree.

The claim still needs `ReadWriteMany` when more than one runtime pod runs concurrently — `subPath` isolates directories, not mounts.

*Alternatives considered:* one claim per conversation via a `volumeClaimTemplate` (rejected: the manager would have to create and garbage-collect PVCs, which means new write permissions on a core resource for a component whose posture is deliberately narrow); sharing one checkout across conversations (rejected outright — concurrent agents in one working tree).

### D6: Telemetry stays lossy, and says so

The activity ring is unchanged. What changes is the boundary report: a cursor from a previous manager process is answered with `resync`, and the console renders that as a visible gap. The failure to avoid is a viewer that shows an empty window and reads as "the system was idle" when it means "this process was not running yet".

## Risks / Trade-offs

- **Flipping `persistence.enabled` to `true` breaks installs on clusters with no RWX provisioner** — the PVC sits `Pending` and runtime pods never schedule → the CHANGELOG entry leads with the one-line opt-out (`persistence.enabled=false`), `NOTES.txt` prints how to diagnose a Pending claim, and CI/demo values set it false explicitly. `helm upgrade` on an existing release is unaffected unless values are reset.
- **`status.runs[]` grows with delivery markers** → markers are channel names on an already-bounded list; the existing run-count bound covers them.
- **Backstop re-delivery could double-post if an adapter posts and then fails to complete the op** → unchanged from today's at-least-once contract; the stable op id gives adapters a better dedup key than the old counter did.
- **Workspace directories accumulate in the claim as conversations close** → off by default, sized by the operator, and documented; no reconciler deletes from a PVC. See Open Questions.
- **Cooldown state on `SignalSource.status` grows with fingerprint churn** → bounded list plus TTL pruning; a source producing more distinct fingerprints than the bound loses the oldest suppression, which degrades to today's behavior rather than to a broken one.
- **A `SignalSource` deleted and recreated loses its suppression** → acceptable: recreating the source is an explicit operator act.

## Migration Plan

1. API additions are all optional fields (`AgentRuntime.spec.workspace`, `Conversation.status.runs[].delivered`, `SignalSource.status` cooldown entries) — regenerate deepcopy and CRDs; old objects remain valid and read as "nothing delivered yet, nothing suppressed yet".
2. First reconcile after upgrade sees completed runs with no delivery markers. To avoid re-posting history, treat runs that completed **before** the controller started as delivered — backfill markers on first observation rather than enqueueing sends. This is the one migration hazard: without it, an upgrade re-posts every recent answer to every bound thread.
3. Chart minor bump; `CHANGELOG.md` entry newest-first covering the `persistence.enabled` default flip, the opt-out, and the new workspace block.
4. Rollback: revert the chart and the image. The new CRD fields are ignored by the old manager; the home PVC carries `helm.sh/resource-policy: keep`, so no data is destroyed by a downgrade.
5. Verify on the live cluster with a server-side dry-run before applying, then a live task: restart the manager between run completion and delivery and confirm the answer still lands.

## Open Questions

- **Workspace directory GC.** Nothing reclaims `<claim>/<conversation>` after a conversation is deleted. Options: leave it to the operator (documented growth, simplest, and the default-off posture limits the blast radius); have the runtime prune sibling directories older than N days on startup (requires mounting the claim root, which weakens the isolation D5 buys); or a chart-shipped CronJob. Leaning to "document it" for this change and revisit if the feature sees use.
- **Is `sendSeq` worth keeping at all?** Acks and notices could take conversation-scoped stable ids too, making every send derivable. Out of scope here — a general-surface notice has no conversation to derive from — but worth naming.
- **Should the cooldown bound be configurable per source?** Starting with a single compiled bound; a source that needs more is a signal to reconsider the grouping configuration rather than the bound.
