# web-chat-deployment

## ADDED Requirements

### Requirement: Default web channel deployed by the chart
The Helm chart SHALL create a web `Channel` CR by default (`webChannel.enabled: true`), named by `webChannel.name` (default `web`), with `defaultProfileRef` settable via `webChannel.defaultProfile`. Setting `webChannel.enabled: false` SHALL render no web-channel resources. The template SHALL follow the same CRD-dependency caveats as the existing `demo.yaml` pattern.

#### Scenario: Fresh install yields a working chat
- **WHEN** the chart is installed with default values (and CRDs enabled)
- **THEN** a web Channel CR and its auth Secret exist, and the chat UI is reachable through the manager Service's API port

#### Scenario: Opt-out renders nothing
- **WHEN** the chart is rendered with `webChannel.enabled: false`
- **THEN** no Channel CR, auth Secret, or web-channel values appear in the output

### Requirement: Auth token Secret generated by default, stable across upgrades
With `webChannel.auth.enabled: true` (the default) and no `existingSecret`, the chart SHALL generate a random token Secret and reference it from the Channel's `authTokenSecretRef`; the token SHALL survive `helm upgrade` (lookup-based reuse), falling back to fresh generation where `lookup` is unavailable (template-only/GitOps rendering — documented, with `existingSecret` as the stable alternative). With `existingSecret` set, the chart SHALL reference it and create no Secret. With `auth.enabled: false`, the Channel SHALL have no `authTokenSecretRef`.

#### Scenario: Upgrade keeps the token
- **WHEN** `helm upgrade` runs against a release whose generated token Secret exists
- **THEN** the Secret's token value is unchanged

#### Scenario: Existing secret referenced verbatim
- **WHEN** `webChannel.auth.existingSecret` names a user-managed Secret
- **THEN** the Channel references that Secret and the chart creates no token Secret

### Requirement: Optional Ingress scoped to the chat path
The chart SHALL provide an Ingress template, disabled by default, that routes **only the `/chat` path prefix** to the manager Service's API port. It SHALL support class name, host, TLS, and annotations values. The chart SHALL NOT provide any template that exposes the full API port externally (internal endpoints `/work`, `/task`, `/ingest/*` stay cluster-internal); the Service SHALL remain ClusterIP by default.

#### Scenario: Ingress exposes only the chat prefix
- **WHEN** the chart is rendered with `ingress.enabled: true` and a host
- **THEN** the Ingress contains only `/chat`-prefixed path rules targeting the API port

#### Scenario: Disabled by default
- **WHEN** the chart is rendered with default values
- **THEN** no Ingress resource is produced

### Requirement: Web-channel agents need no chat credentials
Dispatch SHALL select delivery instructions by channel kind: work units for web-channel (and chat-less) conversations SHALL instruct the agent that its final printed answer is the deliverable (captured via `/work/done`), with no chat-API credentials or curl steps; Telegram units keep the existing instructions. The message format spec SHALL be phrased channel-neutrally (same HTML subset). Any dispatch fixture changes SHALL be deliberate updates reflecting this behavior.

#### Scenario: Web work unit carries no Telegram delivery steps
- **WHEN** a work unit is dispatched for a conversation on a web channel
- **THEN** its prompt contains the printed-answer delivery instructions and no Telegram Bot API instructions

#### Scenario: Telegram work unit unchanged
- **WHEN** a work unit is dispatched for a conversation on a Telegram channel
- **THEN** its prompt delivery instructions are identical to current behavior
