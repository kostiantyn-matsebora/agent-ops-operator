READ THE RULES, BECAUSE THIS REPORT CANNOT SUMMARISE THEM. You wrote them, so

A ClusterRole IS CLUSTER-WIDE. Whatever these grant reaches every namespace,
INCLUDING this one ({{ .Release.Namespace }}), where the manager, the adapters and the MCP
servers run — so a grant on workloads reaches an agent's own supervisor.

Two things this chart never puts in a rule it writes, and worth keeping out of

  - `agentops.dev`, so Conversations, Pipelines and profiles stay unreadable
    everywhere
  - `secrets`, which buys less than it looks — see below
{{- if $podExec }}

⚠  AND SECRETS ARE READABLE, because you set
   global.agentops.runtimeDefaults.allowPodExecution=true.

   THE KUBELET RESOLVES A SECRET WHEN IT BUILDS A POD. An agent that may create
   a pod mounting one — or exec into a pod that already has one — reads the
   value having never asked the API server for a Secret. The rules refusing
   `secrets` are never evaluated, and nothing in Kubernetes stops it.

   Verified against this exact role on a live cluster: pod created, pod log
   read, secret value returned, with all seven `secrets` verbs denied.

   THE DAMAGE, PLAINLY. An agent can read EVERY Secret in the cluster — database
   passwords, API tokens, TLS private keys, cloud credentials — and can run
   arbitrary code inside your workloads. A prompt injection in an alert body, a
   log line or a chat message is enough to ask it to.

   TURN IT OFF unless you accept that:
     --set global.agentops.runtimeDefaults.allowPodExecution=false
{{- else }}

Pod execution is OFF (global.agentops.runtimeDefaults.allowPodExecution=false),
so the no-Secrets rule HOLDS: an agent cannot create a pod, edit a workload's
pod template, or exec into a container, and those are the ways a Secret is read
without asking for one.

Your agents can still scale, restart, evict, cordon, delete workloads, and edit
ConfigMaps, Services and Ingresses. What they cannot do is run new code.

Turning it on grants the `k8s-admin` tools `pods_run` and `pods_exec` — and,
unavoidably, read access to every Secret in the cluster.
{{- end }}

────────────────────────────────────────────────────────────────────────────
YOUR AGENTS HAVE NO KUBERNETES PERMISSIONS

Every route runs as {{ $floor }}, which is bound to nothing and which this chart
refuses to bind anything to. That is the default and no setting widens it.

An agent still reaches whatever its Pipeline's toolsets and MCP servers give it
— the Kubernetes bundle's MCP server carries its OWN account and its own grant,
which is how a demo install reads the cluster with no runtime permissions at all.

To give ONE route more, declare an account STATING WHAT IT MAY DO, and name it:

  rbac:
    runtime:
      serviceAccounts:
        - name: agentops-runtime-acting
          clusterRoles:
            - name: workloads
              rules:
                - apiGroups: ["apps"]
                  resources: ["deployments"]
                  verbs: ["get", "list", "patch"]

  pipelines:
    - name: <route>
      serviceAccountName: agentops-runtime-workloads

There is no mode to name. A word like `full` is a grant nobody reviewed, and
agentops.runtimeReadRules / runtimeWriteRules in the chart are the rules to copy
from and read.
